### 2026-10-01 (continued) — Real push notifications for Vault Watch, closing the delivery gap

The external review that shaped Guardian's two-surface design explicitly recommended deferring push notifications until the core was solid (see the "(continued 6)" entry) — everything it was waiting on is now done, so this picks that up. Standard Web Push throughout: no Firebase, no third-party SDK, no paid service. A VAPID keypair was generated locally (`web-push generate-vapid-keys` — pure crypto, no account needed); the public half is committed in both `src/lib/pushNotifications.js` and `api/guardian/_notify.js` (non-secret by design — every subscription hands it to the browser's own push service), the private half is `VAPID_PRIVATE_KEY`, a new one-time Vercel env var (see README).

**Design**: a vault's record already in Upstash (from Vault Watch's existing registration) gained a `pushSubscriptions` array — one entry per device/browser that opts in, deduped by the subscription's own endpoint URL. `api/guardian/check.js`'s cron is the one place that naturally sees both a vault's previous and newly-computed check in the same request (`record.lastCheck` vs. the fresh `result`), so that's where `_notify.js`'s `describeTransition` runs — it fires at most one notification per check, and only on a genuine transition (breach newly detected, settlement newly broken, or exit newly ready), never a routine re-confirmation. A subscription the push service reports as gone (410/404) gets pruned automatically rather than retried forever.

**A real bug caught by testing the actual re-registration path, not just the new code in isolation**: `registerVault` used to rebuild the stored record from scratch on every call (`{ ...data, address, registeredAt: Date.now() }`), discarding anything else already on it. Registration is called idempotently on every app load (see `refreshAllVaultState`), so this would have silently wiped every device's `pushSubscriptions` — and reset `registeredAt` — the next time the owner simply opened the app. Fixed by merging onto the existing record instead of replacing it. Caught by actually re-running registration against a subscription that was already stored, not by reasoning about the new code alone — the kind of bug that only shows up when you exercise the *old* code path with the *new* data sitting on it.

**Verification, and its real boundary**: no browser was available in this session to confirm a notification actually renders on a device — that's genuinely outside what a sandboxed CLI environment can check, and is flagged rather than assumed. Everything short of that was verified for real, not just reasoned about:
- `describeTransition`'s no-op paths (missing VAPID key, no subscriptions, no real transition) and its actual alert paths, run directly.
- A full real send attempt against Google's live FCM endpoint, with a genuine P-256 key pair (`node:crypto`'s ECDH) so `web-push`'s own client-side validation would pass — got a real 404 back for the nonexistent endpoint, correctly classified as stale and returned for pruning. This exercises the real VAPID-signing + HTTPS-delivery path against real infrastructure, short of an actual subscriber on the other end.
- The full HTTP surface (`register` → `push-subscribe` POST → `status` → re-`register` → confirm subscription survived → `push-subscribe` DELETE → confirm removed → validation errors for a missing field and an unregistered vault) against the local dev server, which is what caught the `registerVault` bug above.
- `check.js`'s cron endpoint end-to-end with a stored subscription present, confirming the full wiring runs clean (correctly reports `notified: 0` for a vault with nothing to transition from).
- A transient "fetch failed" on the very first request after `npm install web-push` turned out to be Vite's dev server re-optimizing dependencies on that same startup (package-lock.json had just changed) — gone on retry, unrelated to anything built here. Worth naming so it isn't mistaken for a real regression if it resurfaces after some future dependency change.

Posted the three findings from the previous two entries to Tachi's Telegram group (`/tachi_ws` signet handshake failure, `VAULT_STATE_ADVANCE` being unwired, and the `getWatchtowerReceipts` doc/behavior mismatch). Madhu S Gowda (Tachi) responded same-day with real, specific answers to all three:

Live payment detection is now genuinely real end-to-end, not just regtest-verified code.

2. **`VAULT_STATE_ADVANCE` (0x11) — more nuanced than "unwired," but the conclusion doesn't change.** The daemon does now accept the transaction type — but it only records a bare, owner-signed, monotonically-increasing state number, with no balance data and no vault lifecycle changes attached to it. This matches exactly what the previous entry's protocol reasoning already concluded (no safe client-side way to split a vault's on-chain UTXO without quorum-validated reconciliation) — good to have it confirmed by the protocol owner directly rather than resting on this app's own derivation alone.

3. **`getWatchtowerReceipts`'s `vault` parameter — confirmed a real SDK doc bug**, exactly as found: it's a 64-hex VaultID, not an address, and Tachi said they'll fix the doc comment. No code change needed on this end; `_check.js` was already built around the real (not documented) behavior.

Nothing else needed changing to ship this — the live-detection fix was infra-side and transparent to the app, and the other two just update what gets written down, not what gets built.

Pivoted to the watchtower breach-receipt check instead, which turned out to be genuinely buildable — but two assumptions in the previous entry's own writeup needed real verification before trusting them, and both turned out interestingly wrong or incomplete:

1. **The SDK client's own JSDoc for `getWatchtowerReceipts({ vault })` says `vault` is "restrict to one vault address."** Live-tested directly against `rpc-signet.tachibtc.com` with curl: passing a real bech32m address gets `invalid vault id` back. Unit-tested the reversal + derivation against a well-formed 64-hex value (no exceptions, correct 32-byte output), then confirmed the derived id is accepted by the live `/tachi_watchtower/receipts` endpoint (`{"count":0,"receipts":[]}` — a real response, not an error). Recorded honestly rather than rounded up.

Implementation: `api/guardian/_check.js` now derives a VaultID per real funding outpoint (a vault with two deposits has two distinct VaultIDs — `deriveVaultId` is defined per-outpoint, not per-vault-address) and checks `/tachi_watchtower/receipts` for each. Any receipt with `classification !== "legitimate"` is surfaced as a real `breachDetected` alert — the highest-severity signal Guardian now has, above the existing settled/exitReady ones, wired through `getVaultWatchAlert`/`getGuardianMeta` (`vaultDisplay.js`) and a new check row in `RecommendationScreen`. ### 2026-09-26 (continued 8) — Root cause found for the git auto-deploy gap: a "sourceless" GitHub link

The previous entry's git→Vercel auto-deploy mystery got root-caused. Querying Vercel's own API for the project (`GET /v9/projects/:id`) showed `"link": { "type": "github", "repo": "Clavis", ..., "sourceless": true }`. `sourceless: true` means Vercel has a record of which GitHub repo the project points at (enough for the dashboard to display it, enough for `vercel git connect` to report "already connected") but no working GitHub App installation actually backing it — so GitHub never had anywhere to deliver a push webhook to, and Vercel never had a way to pull source automatically. The CLI deploys worked the whole time because they upload local source directly, bypassing GitHub entirely — which is exactly why the workaround happened to work without anyone noticing the real cause.

Fix (on GitHub's side, not Vercel's — nothing here to change in this repo): re-authorize the Vercel GitHub App at github.com/settings/installations and confirm it has access to this specific repo, not just installed-but-scoped-elsewhere. Interestingly, right around when this was fixed, a deployment for the *already-pushed* `ee35e92` commit appeared on its own (`source: "git"`, ~30s before the manual CLI deploy from the previous entry) — consistent with a backlogged webhook finally being delivered once the App had real access, rather than the integration being fundamentally broken the whole time.

This commit is the real test: a plain push with no CLI deploy afterward. If a `source: "git"` deployment shows up for it on its own, the fix holds.

### 2026-09-26 (continued 7) — First real deployment of this session's work; two real, unrelated deploy blockers found and fixed

**Lesson worth keeping:** this session verified Vault Watch's *logic* thoroughly (direct HTTP tests against the live daemon, a full Playwright browser pass) but never actually ran `vercel.json` through a real Vercel build before this — a Hobby-plan cron-frequency limit is exactly the kind of thing that only surfaces at real deploy time, no amount of local/dev-server testing would have caught it. Worth remembering for anything that touches `vercel.json` specifically: it needs a real deploy to validate, not just local dev-server behavior.

### 2026-09-26 (continued 4) — Real unilateral exit, and a real protocol safety finding

Top of the Tier-2 list from the same external review, and the natural next target once Send had worked out the sign/broadcast pattern against this daemon. Unlike everything else built this session, unilateral exit is a pure Bitcoin L1 transaction — it doesn't touch Tachi's ledger (TachiTx envelopes) at all, since the whole point of the exit leaf is that it needs no cooperation from anyone, including the daemon.

**Researched against the live daemon before writing app code**, same discipline as every other real integration this project has done. `buildUnilateralExitPsbt` → `verifyUnilateralExitPsbt` → `signUnilateralExitPsbtAsUser` → `finalizeUnilateralExitPsbt` produced a real, structurally correct, fully-witnessed Bitcoin transaction against a throwaway vault (verified via a Node probe, deleted after). Broadcasting it with a synthetic (nonexistent) funding UTXO got exactly the right Bitcoin Core rejection — `bad-txns-inputs-missingorspent` — proving the transaction passed every real structural/script check and failed only on the one thing this sandbox genuinely can't fake: a real, CSV-matured on-chain deposit (1008 blocks, ~a week on signet — not achievable here, same class of limitation as Send's real-funded-vault gap).

**A real, non-obvious protocol finding, caught by thinking through the design rather than by trial and error:** this session's earlier Send work already established that an off-chain VTXO transfer commits successfully on Tachi's ledger *without ever touching the vault's on-chain Bitcoin UTXO* — the PSBT layer is optional for a ledger-level move. Putting that together with how unilateral exit works: the exit leaf's script (`<1008> OP_CHECKSEQUENCEVERIFY OP_DROP <userKey> OP_CHECKSIG`) lets the user's key spend the **entire** on-chain UTXO once matured, regardless of what's happened at the ledger level since. So after a deposit followed by a real Send, the on-chain UTXO can still show its full original value even though part of that value now belongs (per the ledger) to someone else — a full unilateral exit at that point would overclaim. This isn't a bug in the SDK or a gap in this app specifically; it's exactly why Tachi's protocol has a `TACHI_TX_TYPE_VAULT_BREACH` type, a `BreachEventPayload`, and `tachi_watchtower/*` endpoints — a watchtower specifically watches vault addresses for L1 spends and treats a stale claim as a punishable breach. The real fix on the protocol side is a cooperative "vault state advance" (`TACHI_TX_TYPE_VAULT_STATE_ADVANCE` exists in the SDK) that reconciles on-chain state with the ledger — not implemented here; it needs real interactive cooperation with the operator/quorum and is a materially separate task from what this session had time to research properly.

**Scope decision, stated plainly:** rather than let the app build a technically-broadcastable but breach-able exit, `getVaultExitStatus` computes both the vault's real on-chain UTXO total (`scanForUtxos`, live `scantxoutset` — deliberately NOT Tachi's ledger view) and its real ledger balance (`getVaultBalance`, already existing), and exposes a `settled` flag. The app refuses to offer an exit — with an honest, specific explanation — whenever they've diverged. This is the same "honest boundary over fake completeness" principle as every other real integration in this app, just discovered by protocol reasoning rather than by hitting a wall empirically.

**What's real now:**
- `lib/taurusSdk.js` gained `getVaultExitStatus(mnemonicWords, vault)` (real on-chain UTXOs + real CSV confirmations + the `settled` check above) and `exitUnilaterally(mnemonicWords, vault, destinationAddress, exitCandidates)` (loops every matured on-chain UTXO — `buildUnilateralExitPsbt` only spends one at a time, there's no batching primitive for this leaf — building/verifying/signing/finalizing/broadcasting each as a real Bitcoin transaction via `broadcastRawTransaction`).
- `AppStateContext` replaced the old `exitSecondsLeft` mock timer (a `setInterval` counting down from 47, forever, regardless of anything real) with `exitStatus`/`refreshExitStatus()`, and replaced the old `confirmExit` (which just flipped `exitDone` to `true`) with a real one that calls `exitUnilaterally` and handles partial success/failure honestly.
- `Exit.jsx` rewritten around 4 real states instead of one fake countdown: nothing to exit yet (vault has no real on-chain deposit), exit unavailable (diverged — the safety finding above, with the real BTC amounts on both sides shown), counting down (real blocks remaining + a labeled *estimate*, `lib/vaultDisplay.js`'s new `estimateTimeFromBlocks`, 10 min/block same as Tachi's own docs' assumption), and ready to exit — which now also asks for a real destination address (the old UI never did; "Bitcoin mainnet" was hardcoded with no actual destination, which obviously can't work for a real broadcast).

**Verified with a real Playwright + Chromium session, more rigorously than usual** — because a genuinely successful live exit needs a matured real deposit this sandbox can't produce, this test deliberately mocks the two network responses `getVaultExitStatus` reads (`scantxoutset` via the RPC proxy, and `tachi_vtxoLocked` directly) to exercise all 4 real UI branches deterministically: empty vault, diverged balances (with the exact real BTC amounts asserted), counting down (exact real blocksRemaining and confirmations math asserted), and ready. This is legitimate, not a workaround dressed up as a test — it's exercising this app's own real branching logic against controlled inputs, not claiming any fake protocol interaction succeeded, and no exit is actually confirmed or broadcast in the mocked scenarios. For the "ready" scenario, went one step further and actually clicked "Confirm & exit": since the mocked funding's `scriptPubKey` deliberately doesn't match the test vault's real one, this triggered a REAL rejection from the SDK's own `buildUnilateralExitPsbt` (`"funding.scriptPubKey does not equal vault.p2tr.output — exit must spend this vault"`) — confirming both that the SDK enforces this consistency check and that the app's error handling surfaces it correctly instead of crashing or reporting a false success. Zero console errors across all 4 scenarios plus the error-path click.

**Everything from the external review's Tier-2 list that's achievable without a long real-money wait is now done.** Remaining: real receive-side payment detection (`tachi-sdk-ts`'s `client.watch()` over WSS), and the still-explicitly-out-of-scope items (Guardian backend, HAT/RIP, cooperative vault-state advance).

### 2026-09-26 (continued) — Real PIN encryption: the PIN now protects something

Second item off the same external review's Tier-1 list (after Send): "don't leave the PIN as cosmetic." The project's own "Decisions Worth Remembering" already called this exactly right months ago — "Build it properly (Web Crypto encryption) or leave as-is; no cosmetic middle version" — so this was overdue, not a new idea.

**What was actually happening before this session:** `OnboardingContext.submitLockPin` set an in-memory `lockEnabled` flag and nothing else. `AppLockScreen` then called `setWalletMnemonic(words)` regardless of whether the user set a PIN or hit "Skip for now" — plaintext into `localStorage` either way. There was no re-lock screen anywhere in the app; `lockEnabled` was never even read again after onboarding finished. A PIN, once set, was checked exactly once, at setup, and protected nothing on any later visit — a wallet with a PIN and a wallet without one behaved identically from the second page load onward.

**What's real now:**
- `lib/walletCrypto.js` (new) — `encryptMnemonic(words, pin)` / `decryptMnemonic(pin, blob)`, built entirely on the browser's native `SubtleCrypto`: PBKDF2-SHA256 (210,000 iterations, OWASP's 2023 minimum) derives an AES-256-GCM key from the PIN + a random salt; the mnemonic is encrypted under a random IV. No new dependency — same "audited primitive, not hand-rolled" principle as `lib/crypto-shim.js`. Argon2id (the review's suggestion) was considered and dropped: `SubtleCrypto` has no native Argon2, and a WASM Argon2 library is a real supply-chain addition for a demo app that already leans on "standard and minimal" everywhere else.
- `lib/wallet.js` gained `saveEncryptedVault`/`loadEncryptedVault`/`clearEncryptedVault`/`hasEncryptedVault`, alongside the existing plaintext `saveMnemonic`/`loadStoredMnemonic`. The two storage modes are made mutually exclusive at the storage layer itself (`saveMnemonic` clears the encrypted blob and vice versa) rather than trusting every call site to remember — a device has exactly one active wallet, protected exactly one way.
- `OnboardingContext.submitLockPin` is now async: on PIN confirmation it calls `encryptMnemonic` and persists only the encrypted blob — no plaintext copy is ever written when a PIN is set.
- `AppStateContext` gained real locked-state handling: `vaultLocked` (initialized from `hasEncryptedVault()` at boot), `unlockWithPin(pin)` (decrypts, throws a plain "Incorrect PIN..." message on failure — AES-GCM's auth tag makes a wrong PIN and a tampered blob indistinguishable, which is correct: never leak which one it was), and `unlockWithMnemonic(words)` (brings a mnemonic into the live session's memory only, used both by `unlockWithPin` internally and by `AppLockScreen` right after PIN setup — critically, this does NOT also persist a plaintext copy, which the old `carryWalletIntoApp` effectively did). `walletMnemonic` stays `null` while locked; the mnemonic only exists in memory for the current tab's session, exactly the property the external review asked for ("never store the plaintext mnemonic after the wallet has been locked").
- New `UnlockScreen` (shown by `AppShell` in place of any `/app/*` route whenever `vaultLocked` is true — onboarding routes stay reachable so a locked device can still recover): "Vault locked" / "Your wallet keys are encrypted on this device," a 4-digit PIN entry (factored into a shared `PinDigitInput` component so `AppLockScreen` and `UnlockScreen` share the exact same focus-management logic instead of duplicating it), and a "Recover with recovery phrase" link to `/onboarding/import` for the forgot-PIN case — recovery is re-importing the seed phrase, same as the review suggested, since a real PIN reset that could bypass the encryption would mean the PIN was never real security.
- Fixed a bug caught only by testing the actual recovery path, not by reading the diff: `setWalletMnemonic` (the skip-PIN persistence path) never reset `vaultLocked` to `false`. A user recovering via seed phrase after a PIN-protected device, who then chose "Skip for now," would have `localStorage` correctly holding their new plaintext mnemonic while `AppShell` kept showing the stale `UnlockScreen` forever — the in-memory `vaultLocked` flag never got told the encrypted vault it was gating was gone. Fixed by having `setWalletMnemonic` itself clear `vaultLocked`, since assigning a plaintext mnemonic always means "usable right now."

**Verified with two real Playwright + manually-extracted-Chromium E2E runs** (`apt-get download`/`dpkg-deb -x` for the shared libs, same recipe as every prior session's browser verification — Chromium binary via `npx playwright install chromium`, no `--with-deps` since `sudo` needs a password here):

Zero console/page errors throughout.
2. Recovery-clears-stale-vault path: seeded `localStorage` with a real encrypted blob (generated offline via the same `walletCrypto.js`) to simulate "device already has a PIN from a prior session," confirmed it locks `/app` as expected, recovered via a real (valid-checksum) seed phrase, skipped PIN setup, and confirmed the exact bug described above — before the fix this hung on a stale `UnlockScreen`; after the fix it unlocks immediately, the stale encrypted blob is gone, and a reload correctly stays unlocked on the plaintext path.

**Scope boundary, stated plainly:** this protects the mnemonic at rest on this device against someone with filesystem/localStorage access but not the live PIN — it does not, and was never going to, replace the recovery phrase as the ultimate backup, and losing both the PIN and the phrase means the wallet is genuinely gone, same as any correctly-implemented local encryption. That's the intended model, not a gap.

### 2026-09-26 — Real VTXO Send: resolved the "quorum signs out-of-band" doc gap

Picked up the top item from the previous session's "Next up" list (item 7, VTXO transfer pipeline) and from an external code-review pass of the project ("Send is your most important remaining technical milestone"). Same probe-before-build discipline as the deposit work: wrote throwaway Node scripts against the live signet daemon before touching any React code (deleted after, not committed).

**Found a real gap between the published docs and the SDK's actual surface.** Both `vtxo-quickstart.md` and `vault/vtxo.md` describe the transfer pipeline as: build PSBT → verify → user signs → **"the 5-of-7 KDHT quorum contributes their signatures out-of-band"** → `finalizeVtxoPsbt` (assembles the witness from user + node sigs) → wrap in TachiTx → broadcast. The "out-of-band" step has no corresponding function anywhere in `@tachibtc/taurus-vault-core`, and `tachid`'s own `openapi.json` (pulled from the public `tachibtc/tachi-sdk-ts` repo, same source as last session's docs) confirms it: the only cooperative-signing RPC exposed is `/tachi_signTransaction`, and its summary says explicitly "Cooperatively sign a **vault refund**" — nothing for a generic transfer. So the documented flow describes a step client code cannot actually perform.

**Resolved by testing against the live daemon, not by guessing.** `BuildTachiTxTransferArgs.psbt`'s own doc comment is the real clue: "PSBT from `buildVtxoPsbt`, **in any signing state to publish**." Tested the hypothesis directly: built a PSBT, had the user sign it (`signVtxoPsbtAsUser`), deliberately skipped node cosigning, confirmed `finalizeVtxoPsbt` fails as expected (`"input[0] has 0 valid node signatures on the cooperative leaf, needs at least 5"`), then wrapped the *unfinalized*, merely user-signed PSBT in a TachiTx TRANSFER envelope, signed that with `signTachiTx`, and broadcast it anyway. **The daemon accepted it and committed it** — `waitForTachiTxCommit` returned `code: 0, state: "committed"`, and the spent VTXO's record correctly flipped to `spent: true`. Ran this twice more with two distinct throwaway vaults (A → B, partial amount) and confirmed via the commit status's decoded `vout` that the recipient and change split were exactly correct (30,000 to B, 69,000 change back to A) and the original VTXO was marked spent. Conclusion: the ledger-level `signTachiTx` signature over the TachiTx envelope is the real authorization the daemon cares about for moving a VTXO; the Bitcoin-layer quorum cosigning (`finalizeVtxoPsbt`) only matters for producing an independently-broadcastable *on-chain* transaction, which isn't needed for the VTXO to move on Tachi's own ledger. `sendVtxoTransfer` therefore calls `buildVtxoPsbt` → `verifyVtxoPsbt` → `signVtxoPsbtAsUser` → (deliberately skips `finalizeVtxoPsbt`) → `buildTachiTxTransfer` → `signTachiTx` → `broadcastTachiTx` → `waitForTachiTxCommit`, mirroring `registerDepositOnLedger`'s shape from the deposit work.

**Also confirmed empirically: the daemon ignores `VtxoInput.txid`/`vout` when a `vtxoId` is supplied.** None of the VTXO query endpoints (`getLockedVtxos`, `getAddressVtxos`, `getVtxo`) return a real L1 txid/vout, so there'd be no honest way to supply the "real" one for a VTXO discovered via a query anyway. Tested with an all-zero placeholder txid and the transfer committed correctly regardless — `sendVtxoTransfer` uses that placeholder deliberately, with a comment explaining why rather than leaving it looking like an oversight.

**One boundary this session's testing could NOT reach, and didn't try to fake past:** `sendVtxoTransfer` discovers spendable VTXOs via the existing `getVaultBalance` → `getLockedVtxos(vault.p2tr.address)` path (same call Home/Exit already use for balance display). The throwaway-vtxo trick used above for testing the transfer mechanics mints a *ledger-native* VTXO with no real Bitcoin-layer backing, and confirmed live that `getLockedVtxos` does **not** return those (it tracks VTXOs genuinely locked into a vault's P2TR output on-chain, not just any VTXO owned by the vault's key) — expected, not a bug, but it means coin-selection-from-a-real-deposit is only as verified as the previous session already left it (that session's own note: "Have not yet re-verified against the funded wallet"). Worth a real end-to-end faucet-funded Send test before treating this as fully proven — same class of gap as always with this daemon: mechanics proven live, one integration seam still resting on an earlier session's not-fully-closed verification.

**UI changes:** `Transfer.jsx`'s Send tab now has real busy (`"Sending..."`, disabled button) and error states instead of only ever showing success, and the recipient field's placeholder/copy was corrected from "Lightning address or VTXO invoice" (never true — this app has never had a Lightning or invoice path) to explain that a transfer target must be another Tachi vault's P2TR address, matching what `xOnlyFromAddress`'s validation actually requires. Success screen now also shows the real Tachi ledger tx hash, not just the amount, since a demo is more convincing when there's something concrete to point at.

### 2026-08-15 (continued 3) — Real faucet funds, real bugs, both fixed

A public signet faucet funded a generated wallet and a real on-chain deposit succeeded — the first real money movement in the app. Registration (the step added in the previous entry) then failed with `(0, import_browser_external_crypto.createHash) is not a function` on Deposit's success screen. Investigated and fixed two separate, real, browser-only bugs — neither would show up in Node CLI testing, same lesson as the earlier Buffer/fetch bugs:

1. **`createHash is not a function`.** `@tachibtc/taurus-vault-core`'s compiled bundle does `import { createHash } from "crypto"` (Node's builtin) for its TachiTx hashing — no browser equivalent, and Vite just externalizes it rather than failing the build, so the break only surfaces at the moment that code path actually runs. First tried `crypto-browserify` (the standard fix for this class of problem) — worked, but pulled in a known-vulnerable `elliptic` transitive dependency (via `browserify-sign`, for ECDSA/RSA we never call, since actual signing goes through the wallet-aggregator's own audited signer). Tried `create-hash` alone next — narrower, but its browser build needs Node's `stream`/`events` too (via `cipher-base`), same whack-a-mole one level down. Settled on a ~30-line custom shim (`src/lib/crypto-shim.js`) wrapping `@noble/hashes` — audited, zero-dependency, already in the tree transitively (bip32/bip39/bitcoinjs-lib all use it) — matching the exact narrow shape every call site actually needs (`createHash("sha256").update(bytes|string[, "utf8"]).digest([  "hex"])`, confirmed by grepping every `createHash` call in the compiled dist first, not guessed). Verified the shim against a known SHA256 test vector before trusting it. Aliased in `vite.config.js` — had to use an absolute filesystem path (`fileURLToPath(new URL(...))`), not a `/src/...` root-relative string; the dev server's dependency pre-bundler resolves aliases from a different working directory than `vite build` does, so a leading `/` was read as an OS-absolute path in dev only (`No such file or directory`) despite building fine.
2. **A second bug the first one was masking.** Once the hash worked, `broadcastTachiTx`'s POST to `/tachi_txBroadcastSync` hit the exact same CORS gap as the raw Bitcoin RPC proxy (see the original CORS entry below) — Tachi's daemon doesn't send `Access-Control-Allow-Origin` on any POST route's preflight, only GET. Generalized `api/rpc-proxy.js` and its `vite.config.js` dev-server equivalent to accept an optional `?path=`, and added `getRpcProxyUrl(path)` to `lib/wallet.js`. One wrinkle: `broadcastTachiTx` (unlike `BitcoinCoreRpcClient`) does its own strict URL-scheme check (`new URL(url)` with no base, CWE-319 guard) — a bare relative proxy path throws "Invalid URL" there, so `getRpcProxyUrl` builds a full `${window.location.origin}/api/rpc-proxy?...` URL instead, with `allowInsecureHttp` scoped to `import.meta.env.DEV` (Vercel is always `https://`; only local `npm run dev` is `http://`).

Verified both fixes together end-to-end in a real headless-Chromium session (not just the build succeeding): dynamically imported `lib/wallet.js`/`lib/taurusSdk.js` from a live page context, generated a fresh wallet, called `registerDepositOnLedger` for real — real nonce, real hash, real broadcast through the now-fixed proxy, real `waitForVtxoCommit` confirmation, real `vtxoId` back, zero console errors. ### 2026-08-15 (continued) — Making it actually work in a browser

Everything in the "confirmed API shapes" section above was validated with a **Node CLI script first** (`node --eval` against `src/lib/wallet.js` and `taurus-vault-core` directly) before touching any React code — real mnemonic, real signet address, real `wallet.sync()` balance (0, as expected), real `createVault` against the live validator quorum (7 keys), real `verifyVaultP2tr` (no throw), real `depositToVault` call that correctly threw `VaultDepositError: Insufficient funds`. That gave high confidence the SDK integration logic itself was right before debugging anything React/browser-specific.

Wiring the same calls into the actual app (via Playwright + manually-extracted Chromium, same setup as earlier sessions — the sandbox's `/tmp` gets wiped between long gaps, so this had to be redone: `apt-get download libnspr4 libnss3 libasound2t64` + `dpkg-deb -x`, `LD_LIBRARY_PATH` pointed at the extracted `.so`s) surfaced two real browser-only bugs and one real infra gap, none of which the Node test could have caught:

1. **`Buffer is not defined`** — crashed immediately on page load, because `AppStateContext.jsx` statically imports `lib/taurusSdk.js`, which imports `@tachibtc/taurus-vault-core`, which (via `bitcoinjs-lib`) references Node's `Buffer` global at module scope. Fixed with `src/polyfills.js` (imports the `buffer` npm package, sets `globalThis.Buffer`) imported as the very first line of `main.jsx` — has to be first, since ES module imports evaluate their whole dependency graph before the importing file's own code runs, so anything after the first import statement is too late.
2. **`Failed to execute 'fetch' on 'Window': Illegal invocation`** — surfaced only once a real network call happened (the deposit attempt). Traced into `taurus-wallet-aggregator`'s compiled bundle (`chunk-V3QPXLNG.js`): `BitcoinCoreRpcClient` does `this.#fetchImpl = config.fetchImpl ?? globalThis.fetch ?? unsupportedFetch` then later calls `this.#fetchImpl(...)` — calling a bare native `fetch` reference through an object property changes its receiver, and browsers' `fetch` implementation throws on that. Their own `RpcConfig.fetchImpl` option exists for exactly this; passing `fetchImpl: (...args) => fetch(...args)` (a plain wrapper, not the native function itself) fixes it because the *wrapper* doesn't care what `this` it's called with.
3. **CORS gap on Tachi's POST `/` endpoint** — after fixing #2, deposit attempts failed with a CORS preflight error. Confirmed via curl that GET routes (`/health`, `/tachi_validators`) send `Access-Control-Allow-Origin: *`, but an OPTIONS preflight against POST `/` (needed for the JSON-RPC calls `depositToVault` makes internally — coin selection, `scantxoutset`, broadcast) comes back with no CORS headers at all, so the browser blocks the real POST before it's even sent. This is on Tachi's side, not fixable from our code. Standard workaround: proxy it through our own backend, since CORS is a browser-only restriction and server-to-server calls aren't subject to it. Added `api/rpc-proxy.js` (Vercel serverless function — pure relay, no keys, no signing, matches the same watch-only boundary as the planned Guardian backend) and a matching `vite.config.js` `server.proxy` entry so the same relative URL (`/api/rpc-proxy?network=signet`) works in both local dev (Vite proxies it) and production (Vercel serves the function). **Open item:** flag this CORS gap to Tachi (Discord/hackathon channel) — would be good for them to fix upstream so the proxy becomes unnecessary, though it's harmless to keep either way.

After all three fixes: full real flow verified in-browser, zero console errors, screenshots confirm real addresses at every step. The deposit itself resolved in ~32 seconds (an internal `scantxoutset`-shaped balance/UTXO check inside `depositToVault`, not the fast Esplora path `wallet.sync()` uses) before correctly reporting insufficient funds — worth knowing so a live demo doesn't look frozen during that wait; consider a slightly more descriptive busy-state message than what's there now if this comes up again.

**VTXO Receive tab fixed** to show the real vault P2TR address instead of the old fictional `vtxo1...` string, via a new shared `ensureRealVault()` on `AppStateContext` (also used by Deposit — one place creates the vault, not two). Verified in-browser: the vault address (`tb1p...`) and funding address (`tb1q...`) are correctly distinct.

**Wallet persistence gap found live** — while testing with a real signet faucet, sent funds to a generated address, then asked whether Home would reflect it. Good question that surfaced two things: (1) Home is still mock, confirmed as a known gap, not a surprise; (2) more importantly, the wallet mnemonic had **no persistence at all** — it was regenerated fresh via `useState(() => generateMnemonicWords())` on every page load, so a browser reload after getting a receive address would silently swap in a brand-new wallet and orphan the just-funded address (funds still safe on-chain, just unreachable through the UI without the original mnemonic). Fixed with `localStorage` persistence (`lib/wallet.js`'s `loadStoredMnemonic`/`saveMnemonic`, wired into `AppStateContext`'s `walletMnemonic` state) — verified with a real reload test in-browser, same address before and after. Plaintext storage is an accepted tradeoff here (signet test coins only), not a pattern to copy for anything holding real value.

## Decisions Worth Remembering

- Guardian recommends, never auto-acts — firm, do not build autonomous execution.
- Backend (when built) is watch-only — never holds keys, never signs/broadcasts.
- Seed generation is 100% client-side, never touches a backend, never logged, no clipboard copy button (deliberate — clipboard is a leak vector).
- PIN lock now does real Web Crypto encryption (AES-GCM + PBKDF2) and re-locks on every load — see 2026-09-26 entry. The "no cosmetic middle version" call this line used to make was followed through on, not walked back.
- Timelock is protocol-fixed at 1008 blocks — never build a duration picker.
- No Google/social auth as a signing mechanism, ever — app-lock convenience only, never key custody.
